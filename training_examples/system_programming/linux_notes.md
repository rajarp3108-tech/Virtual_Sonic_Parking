## 1. What "Linux" actually is

| Layer | Example | Who maintains it |
|---|---|---|
| Hardware | x86-64, ARM | vendors |
| Kernel (Linux) | scheduler, memory, drivers, file system | Linus Torvalds + thousands |
| System libraries | glibc, libstdc++ | GNU, GCC project |
| User space tools | bash, coreutils, git, make | individual projects |
| Distributions | Ubuntu, Debian, Fedora, Arch | packagers assemble the above |

The kernel is only one part. "Linux" as an operating system in practice means
kernel + GNU user space + a distribution's choices about init system, package
manager and desktop.

**Why this matters for the project.** The driver talks only to the kernel
(`printk`, `alloc_chrdev_region`, `copy_to_user`). The application talks to
POSIX, provided by glibc. That is why the C++ half of this project also
compiles and runs on macOS and in WSL, while the driver half cannot.

## 3. File system hierarchy that matters here

```
/dev        device nodes. The driver creates /dev/parking_sensor here.
/proc       a virtual file system: process info as files
/sys        device and driver attributes, including our module parameters
/var/log    conventional place for log files (the project uses ./logs)
/tmp        scratch space
/           the root mount; a daemon chdir()s here
```

Two of these deserve a sentence in a viva:

- `/proc` is not a real file system on disk. It is generated by the kernel
  while you read it. `cat /proc/<pid>/status` is the kernel answering a
  question about a running process.
- `/sys` **is** a real (sysfs) file system, and it is where `module_param`
  values appear as files:

  ```bash
  cat /sys/module/parking_sensor/parameters/interval_ms      # read
  insmod driver/parking_sensor.ko interval_ms=2000           # set at load
  ```

  The third permission digit of `module_param(name, type, 0644)` decides
  whether that file is writable. This project uses `0444`, so the attempt
  fails with `Permission denied` - which is the visible half of the device
  model, and the reason a parameter cannot be changed while the timer is
  mid-flight. That is the sysfs evidence for the device model section of the
  syllabus.

## 4. Permissions

`ls -l` shows `rwxr-xr-x`. Read it as three triples: **owner**, **group**,
**others**, each `rwx`.

A device node needs root:

```
crw------- 1 root root 240, 0 Sep 28 19:02 /dev/parking_sensor
         ^  ^---------- major 240, minor 0
```

So a normal user cannot read the device unless the mode is changed:

```bash
sudo mknod /dev/parking_sensor c 240 0
sudo chmod 666 /dev/parking_sensor      # for a lab machine only
```

`scripts/load_driver.sh` creates the node with `chmod 660`. On a shared lab
machine, be deliberate about this rather than running `chmod 777` on a device.

`umask(022)` in the daemon is what makes new files `rw-r--r--`: the mask
subtracts permissions rather than adding them.

## 5. Bash scripting essentials used in `scripts/`

```bash
#!/usr/bin/env bash          # the "why" of the shebang
set -euo pipefail             # exit on error, on unset var, on any pipe failure
                              #   -u catches typos in variable names
                              #   -o pipefail catches a failure on the left of |
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"   # absolute path
cd "$SCRIPT_DIR/.."

if [ "$(id -u)" -eq 0 ]; then ...; fi        # numeric comparison
for arg in "$@"; do case "$arg" in --flag) ... ;; esac; done
grep -q pattern file && echo found           # && is short-circuit and
[ -c /dev/parking_sensor ] && mknod ...      #   perfect for "if it exists"
printf '\033[1;32m%s\033[0m\n' "green text"   # ANSI colour
trap cleanup EXIT                            # always run cleanup
```

Why `set -e` is not enough on its own: it does not catch an unset variable, it
does not catch a failure in the middle of a pipeline, and it does not fire in a
function called in a condition. `set -euo pipefail` covers the three cases that
actually bite in a build script.

## 6. cron

```bash
crontab -e
```

```
# minute hour dom mon dow  command
*/5 * * * *   /usr/local/bin/status_client --port 9000 --count 1 >> /tmp/status.log
0   6 * * 0   /usr/local/bin/parking_weekly_report.sh
@reboot      /usr/local/bin/parking_monitor --daemon
```

**Use in this project.** A cron entry is one honest alternative to a daemon:
`@reboot` starts the monitor at boot, and a `*/5` entry could sample the status
without a long-running process at all. The SRS asks for a daemon, so that is
what the project implements - but the cron route is worth one line in the
report, because "why a daemon instead of cron?" is a good question.

## 7. Git, concretely

```bash
git init
git config user.name  "Your Name"
git config user.email "you@example.com"
git status                      # what changed
git add driver/parking_sensor.c # stage one file
git add -A                      # or stage everything
git commit -m "feat(driver): character device with kernel timer"
git log --oneline --graph --all # the stage history
git diff                        # unstaged changes
git diff --staged               # staged changes
git show HEAD~1                 # the previous commit in full
git switch -c feature/driver    # branch, then work, then merge
git switch main
git merge --no-ff feature/driver
git reset --soft HEAD~1         # undo the last commit, keep the changes staged
git revert <sha>                # a new commit that undoes an old one
git restore app/src/main.cpp    # discard working-tree changes to one file
```

`reset` rewrites history; `revert` adds a commit. On a shared repository always
use `revert`.

**Commit message shape** used throughout this project:

```
<type>: <what changed in one line>

<why it changed, and anything a reader could not guess>
```

Types used: `feat`, `fix`, `test`, `docs`, `chore`, `build`.
